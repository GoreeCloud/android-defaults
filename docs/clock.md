# Clock — Android development preview

## User experience

- Floating bottom navigation: **Alarms**, **Timer**, **Stopwatch**, **Settings**, with selected-state indicators, accessible tab group semantics, and labels. Tablet-width layouts cap the centered content column at 840 dp and the floating bottom dock at 560 dp; phones continue to fill their available width. These are responsive source constraints, not proof of rendered phone/tablet acceptance.
- Alarms: honor the Android 12/24-hour preference and localized AM/PM markers consistently in the next-alarm summary, alarm rows and spoken switch labels; distinguish alarm-specific edit/delete accessibility actions. Add a local alarm, edit its time, enable/disable it, select repeat weekdays and delete it. Stable full 64-bit PendingIntent URI identities prevent request-code hash collisions; on rescheduling/upgrades, old hash-only requests are canceled. Alarm creation also guards against same-millisecond ID reuse, while notifications use ID-specific tags. Scheduling uses Android AlarmManager.setAlarmClock and reschedules following reboot, time/time-zone adjustment and app replacement.
- Timer: set a countdown with validated 00–59 minute/second fields (never silently clamp invalid values), start, pause, resume and reset. An AlarmManager alarm notifies the user on completion even when the interface is not foregrounded.
- Stopwatch: start, pause, reset and capture laps, with elapsed time maintained against Android elapsedRealtime. Fine-grained foreground updates run only while the app is visible; background rendering is suspended without stopping elapsed time.
- Settings: system/light/dark appearance; notification and exact-alarm access state and shortcuts to system controls.

## Platform behavior

The app is a Kotlin/Jetpack Compose Android module for API 26–35. Alarms and background timers require both notification permission (Android 13+) and exact-alarm access (Android 12+), which users explicitly grant in Android settings. If missing, the app refuses to mark a newly enabled alarm or timer as scheduled. It also checks Android's app-level notification switch, alert-channel importance and sound: disabled or silenced channels must not count as working audible alert access, and enabled alarms display an access warning until relevant settings are restored. Returning to Clock restores saved enabled alarm schedules and an unfinished timer after permission/channel access returns; the runtime notification-permission callback also explicitly reconciles those schedules even if Android does not deliver another Activity resume event. Existing PendingIntent identities prevent duplicate scheduled triggers. If a previously persisted timer is past due on return to Clock, it displays a notice instead of leaving a misleading 00:00 countdown. The completion receiver now preserves the expired deadline if Android rejects its notification post (for example after notification permission is revoked), so the next foreground recovery can warn instead of silently losing the event. A successful notification API post does **not** guarantee that a notification sounded: Do Not Disturb, channel configuration, OEM restrictions and locked-screen behavior still need physical testing. This is recovery behavior, not proof of audible notification delivery.

Notifications use a high-importance alarm-sound channel. Android notification controls, Do Not Disturb, device power policies and OEM behavior can affect alert delivery and sound. This is an **initial local Clock implementation**, not an independently device-tested safety-critical alarm substitute. No fullscreen alarm ringing, custom ringtones, persistent lap history, or cloud synchronization is implemented.

The app does not request INTERNET; stored times are local to the device and are not backed up. Besides `android:allowBackup="false"`, explicit extraction rules exclude app-private data from cloud backup and device-to-device transfer on Android 12+ (plus legacy full-backup rules for API 26–30), because some OEMs do not disable device transfers solely based on the manifest flag. Cross-platform transfer to iOS has separate Android 16 QPR2 requirements and still needs platform-specific verification; no matching iOS app identity is configured. Both clock receivers are non-exported: the alarm receiver accepts only app-owned PendingIntents, while the rescheduling receiver subscribes to system boot/time/package/permission broadcasts. The merged APK manifest is checked in CI so these entry points cannot silently become externally exported. A stopped/rebooted stopwatch is restored conservatively and its elapsedRealtime session is invalidated when the underlying monotonic clock resets.

## Engineering validation

An additional, isolated GitHub-hosted Android API 35 emulator smoke job now tests real Android package/receiver privacy flags, 64-bit alarm PendingIntent separation, and the native four-tab Compose navigation. This is an **emulator-only development acceptance gate** and does not demonstrate physical-device audibility, OEM battery behavior, real TalkBack focus, or Android 16 transfer behavior. The external emulator-runner action is source-reviewed and pinned to an immutable upstream commit; it installs SDK/emulator components only on the disposable CI runner. The same isolated emulator job now also captures **Alarms-page light/dark screenshots** at phone and simulated landscape tablet dimensions as a separate PNG artifact. Capturing valid PNG bytes is not visual acceptance: inspect the actual screenshots for spacing, contrast and hierarchy, and still validate real-device/assistive-technology behavior. Each capture script changes only disposable emulator settings (system night mode and virtual display size/density), never a linked owner device. The screenshot job must pass and the actual screenshots must be reviewed before reporting visual QA results.

The GitHub Actions workflow pins its checkout, Java setup, Gradle setup and artifact-upload actions to verified upstream **full commit IDs** rather than mutable major-version tags. It runs a source-level pinning regression check, disables persistent checkout credentials, and restricts job permissions to read-only repository contents. The supported actions are run on GitHub-hosted runners, and the workflow must pass before this security maintenance is considered validated. Upgrade and review action pins deliberately; a pinned commit prevents moving-tag drift but does not guarantee an upstream action is safe.

CI runs :clock:testDebugUnitTest, :clock:assembleDebug and :clock:lintDebug, and validates source backup-exclusion policies plus the packaged APK's app identity, sensitive-permission restrictions, non-exported receiver declarations, and backup-rule resources.

**Historical baseline:** [GitHub Actions #42338343449](https://github.com/GoreeCloud/android-defaults/actions/runs/42338343449) passed on commit `30f0458` (19 JVM tests, debug APK, Lint, permission and backup policy). The later combined Clock/Dialer/Contacts [CI at integration head `c0479dd`](https://github.com/GoreeCloud/android-defaults/actions/runs/42758735379) passed source tests but its four screenshot images were obstructed by a launcher ANR. The [current draft integration PR #45](https://github.com/GoreeCloud/android-defaults/pull/45) includes newer alarm/timer reliability changes; CI results are associated with their exact head and cannot be inferred from these earlier runs. No physical audible-alert or release acceptance is claimed.

**Partial physical verification:** A previous validated debug build (`46be8f3`, not the latest privacy commit) installed successfully on an authorized API 36 Android handset without taking over the foreground activity. Installed APK byte identity was verified. No Clock launch, notifications, exact-alarm permission grant, audible alert, reboot test, visual/TalkBack acceptance, or OEM backup/transfer validation has occurred. A **standalone debug QA candidate** for commit `30f0458` was uploaded to the mandatory `GoreeCloud/Artifacts` folder ([Drive APK](https://drive.google.com/file/d/17_K5I1TvpuUcBGHPj0eqANd2SHV1BO3W/view)), with SHA-256 `cfdebaa7b84e9277ac6a6ce4cd8875dfbe3dd88ed6377dd793183c6f23e175c6` and verified download readback. ## Visual screenshot integrity checkpoint — November 15, 2026

The [previous combined emulator CI run](https://github.com/GoreeCloud/android-defaults/actions/runs/42758735379) uploaded four apparently valid PNGs (light/dark phone and tablet), but **each rendered image was obscured by an Android "Pixel Launcher isn't responding" system dialog**. Valid PNG bytes and a green capture step did not represent visual acceptance. The affected artifact was independently opened and reviewed; this is a captured emulator UI blocker, not evidence of an app crash.

The follow-on Clock QA guard in [this Clock screenshot QA review branch](https://github.com/GoreeCloud/android-defaults/tree/fix/clock-qa-blocked-screenshots-20261115) checks that the Clock activity owns Android's focused window before and after a screenshot. When an ANR/system dialog has focus, the capture is rejected rather than labeled as successful; it does not dismiss other apps' dialogs or interact with physical phones. Synthetic offline tests cover both refusal on an actual non-QEMU-target mock and refusal when the disposable-emulator mock displays an ANR dialog. **The new guard must pass source CI and real emulator screenshot capture before it can be considered verified.** Device UI quality, TalkBack and physical audible-alarm acceptance remain separate.

## All-tab visual QA expansion (review stage)

The emulator capture script now requests **16 separate screenshots**: four tab pages (**Alarms, Timer, Stopwatch, Settings**) in light/dark and phone/tablet layouts. It preserves the original four Alarms artifact names for compatibility. To navigate, it extracts a visible bottom-dock tab's bounds from Android's accessibility hierarchy in a pure Python parser, refuses missing or ambiguous nodes, verifies expected page text, and confirms Clock retains focused-window ownership before/after each screenshot. All UI taps occur only after the same fixed-serial QEMU verification on a disposable CI emulator. The fixture-only parser regressions run offline before Gradle; they cannot interact with owner devices.

A completed run and four-tab screenshot **visual inspection** are still necessary before claiming acceptance. This source does not by itself validate landscape phone, font scaling, TalkBack, OS 36.1 cross-platform transfers, production permission behavior, or real audible alarms.
