# Clock — Android development preview

## User experience

- Floating bottom navigation: **Alarms**, **Timer**, **Stopwatch**, **Settings**, with selected-state indicators, accessible tab group semantics, and labels. Tablet-width layouts cap the centered content column at 840 dp and the floating bottom dock at 560 dp; phones continue to fill their available width. These are responsive source constraints, not proof of rendered phone/tablet acceptance.
- Alarms: honor the Android 12/24-hour preference and localized AM/PM markers consistently in the next-alarm summary, alarm rows and spoken switch labels; distinguish alarm-specific edit/delete accessibility actions. Add a local alarm, edit its time, enable/disable it, select repeat weekdays and delete it. Stable full 64-bit PendingIntent URI identities prevent request-code hash collisions; on rescheduling/upgrades, old hash-only requests are canceled. Alarm creation also guards against same-millisecond ID reuse, while notifications use ID-specific tags. Scheduling uses Android AlarmManager.setAlarmClock and reschedules following reboot, time/time-zone adjustment and app replacement.
- Timer: set a countdown with validated 00–59 minute/second fields (never silently clamp invalid values), start, pause, resume and reset. An AlarmManager alarm notifies the user on completion even when the interface is not foregrounded.
- Stopwatch: start, pause, reset and capture laps, with elapsed time maintained against Android elapsedRealtime. Fine-grained foreground updates run only while the app is visible; background rendering is suspended without stopping elapsed time.
- Settings: system/light/dark appearance; notification and exact-alarm access state and shortcuts to system controls.

## Platform behavior

The app is a Kotlin/Jetpack Compose Android module for API 26–35. Alarms and background timers require both notification permission (Android 13+) and exact-alarm access (Android 12+), which users explicitly grant in Android settings. If missing, the app refuses to mark a newly enabled alarm or timer as scheduled. It also checks Android's app-level notification switch, alert-channel importance and sound: disabled or silenced channels must not count as working audible alert access, and enabled alarms display an access warning until relevant settings are restored. Returning to Clock restores saved enabled alarm schedules and an unfinished timer after permission/channel access returns; the runtime notification-permission callback also explicitly reconciles those schedules even if Android does not deliver another Activity resume event. Existing PendingIntent identities prevent duplicate scheduled triggers. If a previously persisted timer is already past due when Clock resumes but its completion broadcast did not clear it, Clock clears the stale countdown and displays a notice instead of leaving a misleading 00:00 timer running. This is recovery behavior, not proof of audible notification delivery.

Notifications use a high-importance alarm-sound channel. Android notification controls, Do Not Disturb, device power policies and OEM behavior can affect alert delivery and sound. This is an **initial local Clock implementation**, not an independently device-tested safety-critical alarm substitute. No fullscreen alarm ringing, custom ringtones, persistent lap history, or cloud synchronization is implemented.

The app does not request INTERNET; stored times are local to the device and are not backed up. Besides `android:allowBackup="false"`, explicit extraction rules exclude app-private data from cloud backup and device-to-device transfer on Android 12+ (plus legacy full-backup rules for API 26–30), because some OEMs do not disable device transfers solely based on the manifest flag. Cross-platform transfer to iOS has separate Android 16 QPR2 requirements and still needs platform-specific verification; no matching iOS app identity is configured. Both clock receivers are non-exported: the alarm receiver accepts only app-owned PendingIntents, while the rescheduling receiver subscribes to system boot/time/package/permission broadcasts. The merged APK manifest is checked in CI so these entry points cannot silently become externally exported. A stopped/rebooted stopwatch is restored conservatively and its elapsedRealtime session is invalidated when the underlying monotonic clock resets.

## GoreeCloud UI

The Compose light/dark colors are mapped from the versioned GoreeCloud UI token reference in GoreeCloud/gc-ui, tokens/gc.v1.tokens.json; product acceptance still requires rendered phone/tablet screenshots and accessibility review. The bottom dock uses a purposeful Lens-inspired raised surface with a solid fallback. The adaptive launcher icon uses approved GC UI semantic colors and a custom vector clock dial; actual launcher rendering remains subject to device review. System status/navigation icon contrast follows the selected appearance.

## Engineering validation

The GitHub Actions workflow pins its checkout, Java setup, Gradle setup and artifact-upload actions to verified upstream **full commit IDs** rather than mutable major-version tags. It runs a source-level pinning regression check, disables persistent checkout credentials, and restricts job permissions to read-only repository contents. The supported actions are run on GitHub-hosted runners, and the workflow must pass before this security maintenance is considered validated. Upgrade and review action pins deliberately; a pinned commit prevents moving-tag drift but does not guarantee an upstream action is safe.

CI runs :clock:testDebugUnitTest, :clock:assembleDebug and :clock:lintDebug, and validates source backup-exclusion policies plus the packaged APK's app identity, sensitive-permission restrictions, non-exported receiver declarations, and backup-rule resources.
